**22.** 括号生成 - 题解
====

# 题目描述

数字 `n` 代表生成括号的对数，请你设计一个函数，用于能够生成所有可能的并且 **有效的** 括号组合。

**示例 1：**
```
输入：n = 3
输出：["((()))","(()())","(())()","()(())","()()()"]
```

**示例 2：**
```
输入：n = 2
输出：["(())","()()"]
```

**提示：**
- `1 <= n <= 8`

---

# 思路一：暴力枚举（未实现）

## 解题思路

**核心思想**：枚举所有长度为 `2n` 的括号串，然后判断每个是否有效。

这是我最自然的想法：每一步决定放 `(` 还是 `)`，当字符串长度达到 `2n` 时，用栈判断是否为有效括号串。

**算法流程**：
1. DFS 枚举，每一步选择放 `(` 或 `)`
2. 当字符串长度达到 `2n` 时，用栈判断有效性
3. 有效则加入答案

## 复杂度
- 时间复杂度：`O(2^(2n) × n)` —— 2^(2n) 个叶子节点，每个判断 O(n)
- 空间复杂度：`O(n)` —— 递归栈深度

## Code
```cpp
// 未实现的伪代码思路
void dfs(int remain, string path) {
    if (remain == 0) {
        if (isValid(path)) ans.push_back(path);
        return;
    }
    dfs(remain - 1, path + '(');
    dfs(remain - 1, path + ')');
}
```

**问题/优化方向**：
- 大量无效分支（如 `)))(((` 这种明显不合法的串也会被搜索到）
- 可以在搜索过程中就剪掉无效分支，而不是搜完再判断

# 思路二：插入法（❌ 失败尝试）

## 解题思路

**核心思想**：基于 `n-1` 的所有有效括号串，插入一对新的 `()` 来生成 `n` 的解。

我最初想到这个方法：构造一个层次的二叉树，从上层到下层的转移过程中，新加的括号可以插入哪些位置，只需要满足新插入的 `)` 在新插入的 `(` 的右边。

**尝试过程**：
1. n=1 时：`["()"]`
2. 基于 `"()"` 插入一对新括号 `()`：
   - 外层插入：`(())`
   - 中间/内层插入：`()()`
3. 发现问题：**重复！**
   - 当基于 `(())` 继续插入时，外层插入和内层插入可能得到相同结果
   - 比如 `(())` 插入 `()` 到外层得到 `(()())`，插入到内层也得到 `(()())`

**为什么失败**：
- 这种方法会产生重复结果
- 如果要去重，需要使用哈希表，增加额外空间和时间开销
- 实现复杂度比想象中高

**关键转折**：
在面试官引导下，我意识到不应该执着于"从 n-1 推 n"的思路，而是应该**直接构造长度为 2n 的字符串**，在构造过程中就保证有效性。

# 思路三：DFS + 剪枝（✅ 推荐解法）

## 解题思路

**核心思想**：在构造过程中通过剪枝条件保证有效性，只搜索有效状态。

这是在面试官引导下找到的正确方向：
- 面试官问："从空串开始，每一步能放什么？"
- 我答："可以放 `(` 或 `)`"
- 面试官问："什么时候可以放 `(`？什么时候可以放 `)`？"
- 我恍然大悟："左括号不超过 n 个，右括号不能超过左括号！"

**关键状态定义**：
- `left`：已放置的左括号数量
- `right`：已放置的右括号数量

**剪枝条件**：
1. `left > n`：左括号超过总数，非法
2. `left < right`：右括号比左括号多，非法（会出现 `")("` 这种情况）

**算法流程**：
1. 初始状态：`left=0, right=0, path=""`
2. 如果 `left < n`，可以放置 `(`，递归
3. 如果 `right < left`，可以放置 `)`，递归
4. 当 `left + right == 2n` 时，得到一个有效解

## 复杂度
- 时间复杂度：`O(C_n × n)` —— C_n 是第 n 个卡特兰数，`\frac{1}{n+1}\binom{2n}{n}`，约为 `\frac{4^n}{n^{3/2}}`
- 空间复杂度：`O(n)` —— 递归栈深度，使用回溯（引用传递 + 恢复）优化空间

## Code
```cpp
/*
 * @lc app=leetcode.cn id=22 lang=cpp
 *
 * [22] 括号生成
 */

// @lc code=start
#include <vector>
#include <string>

using namespace std;

class Solution {
public:
    vector<string> ans;
    int n;

    // 剪枝条件判断
    auto is_prune_case(int remain_braket, int left, int right, const string& path) -> bool {
        // left > n: 左括号超过总数
        // left < right: 右括号比左括号多，非法
        if (left < right || left > n) {
            return true;
        }
        return false;
    }

    // 判断是否为有效括号串（剪枝充分时可省略）
    auto is_vaild(int left, int right, const string& path) -> bool {
        if (left != right) {
            return false;
        }
        // 由于剪枝条件保证了 left >= right 始终成立
        // 到达叶子时 left == right == n，必然有效
        return true;
    }

    auto dfs_visit(int remain_braket, int left, int right, string& path) {
        // 到达叶子节点
        if (remain_braket == 0) {
            if (is_vaild(left, right, path)) {
                ans.push_back(path);
            }
            return;
        }

        // 剪枝
        if (is_prune_case(remain_braket, left, right, path)) {
            return;
        }

        // 尝试放置左括号
        path.push_back('(');
        dfs_visit(remain_braket - 1, left + 1, right, path);
        path.pop_back();  // 回溯

        // 尝试放置右括号
        path.push_back(')');
        dfs_visit(remain_braket - 1, left, right + 1, path);
        path.pop_back();  // 回溯
    }

    vector<string> generateParenthesis(int n) {
        this->n = n;
        string path("");
        dfs_visit(2 * n, 0, 0, path);
        return ans;
    }
};
// @lc code=end
```

**问题/优化方向**：
- `is_vaild` 在剪枝充分的情况下可以省略，因为到达叶子时必然满足 `left == right == n`
- `is_prune_case` 中的 `right > n` 条件多余，因为 `right <= left <= n` 已保证

# 思路四：搜索问题通用框架（延伸讨论）

## 核心洞察

通过这道题，我总结了解决搜索问题的通用框架：

**搜索问题 = 在状态图上遍历，通过剪枝和去重让遍历逼近真实解空间**

### 四个层次：
1. **状态定义**：一个节点包含什么信息？必须足够决定后续决策，但不过度冗余
2. **转移规则**：从当前状态能扩展出哪些候选状态？
3. **目标条件**：哪些状态是合法解？
4. **约束与去重**：哪些状态不必继续扩展？哪些状态本质相同需要合并？

### 两类优化：
1. **控制重复**：在状态定义和转移规则中消除重复，而不是搜完再去重
2. **剪枝策略**：
   - 可行性剪枝（本题：`left < right`）
   - 最优性剪枝（分支限界）
   - 支配剪枝（DP 的核心）

### 回溯的本质：
回溯 = **DFS_VISIT** + 状态恢复，目的是用 `O(深度)` 的空间系统性地遍历解空间。

对比：
- 按值传递：代码简洁，空间 `O(n^2)`，频繁拷贝
- 引用传递 + 回溯：代码稍复杂，空间 `O(n)`，只需 push/pop

# 总结对比

| 思路 | 时间复杂度 | 空间复杂度 | 特点 |
|------|-----------|-----------|------|
| 暴力枚举 | `O(2^(2n) × n)` | `O(n)` | 枚举所有可能再判断，大量无效搜索 |
| 插入法 | `O(C_n × n)` + 去重开销 | `O(C_n)` | 会产生重复，需要去重，实现复杂 |
| DFS + 剪枝 | `O(C_n × n)` | `O(n)` | ✅ 推荐，状态定义清晰，天然不重不漏 |

# 关键词与核心洞察

## 关键词
- **卡特兰数**：有效括号组合数是第 n 个卡特兰数 $C_n = \frac{1}{n+1}\binom{2n}{n}$，这解释了为什么剪枝后的节点数是这个量级
- **剪枝**：不是在叶子节点判断合法性，而是在搜索过程中就剪掉不可能成为合法解的分支
- **回溯**：引用传递 + 状态恢复，空间优化的 **DFS_VISIT** 实现方式
- **状态定义优化**：虽然最终答案需要完整的 path 字符串，但剪枝决策只需要 `left` 和 `right` 两个计数变量即可进行剪枝（`left < right` 或 `left > n`），无需每次扫描 path 检查合法性

## Insight

- 🌟 **搜索问题的本质**：不是"会不会遍历"，而是"能否把问题压缩成一个小而准的状态图"。本题的关键在于发现只需要 `left` 和 `right` 两个变量就能做所有决策，不需要存储完整的 path 做判断。

- **剪枝的本质**：通过局部约束（`left >= right`）来保证全局性质（最终串有效）。这是一种贪心思想的延伸——一旦违反局部约束，整棵子树都可以剪掉。

- **去重的最优策略**：不是"搜完再去重"，而是"让重复根本不出现"。本题状态图中的所有的状态都是不重复的，不需要额外的去重机制，这是比插入法更优的根本原因。

## 易错点

- **回溯时遗漏 pop_back**：右分支递归后也必须 `path.pop_back()`，否则后续递归会在错误的 path 基础上继续
- **参数 n 的含义混淆**：递归过程中的 `n` 是剩余步数还是总对数？需要小心处理，建议用类的成员变量存储总对数
- **剪枝条件顺序**：先检查剪枝条件，再递归；如果先修改 path 再检查，会导致回溯混乱
- **边界情况**：`n=0` 时应该返回 `[""]`（空串也是有效括号组合），但题目约束 `n >= 1`，可以忽略

---

**推荐**：面试中使用 **DFS + 剪枝**，状态定义清晰（left, right，path），剪枝条件直观（left < right 或 left > n），代码简洁且复杂度最优。可以主动提及卡特兰数，展示对问题本质的理解。
